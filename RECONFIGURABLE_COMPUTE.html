Where the saved cycles come from

Prefill: A uses each weight tile for 32 tokens; B uses it for 16. Both assign work to all 256 PEs, but B transfers twice as many weight bytes. A reduces combined input and weight transfer cost.

Decode: A assigns useful work to 64 PEs; B assigns it to 128. Covering twice as many outputs per mapping reduces mapping invocations from 2,048 to 1,024 and halves PE preload cycles. Both read the same full 4 MiB weight matrix.

Mapping parameters, evidence, and model boundaries

One complete q_proj invocation: prefill 768×1024×2048, decode 1×1024×2048 (M×K×N), batch 1, Qwen3-0.6B. These are matrix costs, not end-to-end token latency.

A fixes Gr=8, Gc=2 with a maximum 32×32×32 tile. B fixes Gr=8, Gc=4 with a maximum 16×32×64 tile. Both use sr=1, sc=16, two K groups, W/O orders 2/0, and WO-S execution. The M tile clips to the available tokens; input layout becomes 2 for prefill and 0 for decode. “Fixed” here means a fixed spatial mapping policy, not an identical binary for different shapes.

At PE row r and column c: n = r + 16(c mod Gc), K half = floor(c/8), m = dot·(8/Gc) + floor((c mod 8)/Gc). Each PE holds W[K half·16 : K half·16+16, n] and receives I[m, k] down its column.

The exported records pass compiler checks for encodings, buffer capacity, memory-bank conflicts, and exact tile MAC coverage. Performance uses serialized_minisa_v2, including operand loads, PE preload, streaming, gaps/drain, instruction dispatch, and stores. Operands start in their required layouts. Layout conversion, external-memory stalls, host launch, and non-GEMM operations are excluded. These four comparisons are predictions; no new RTL measurements are claimed.

The result compares these two supported mappings and does not establish a universal advantage over every fixed mapping. Reconfiguration and weight setup instructions are included in each program; retaining weights across separate phase programs is not assumed.
